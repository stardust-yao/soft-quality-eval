# info-org-eval

**评测一份回答的「信息组织」好不好**——不是文笔，是读者能不能高效地把散在文中的信息拼成他要的答案。

八项，分两半：**基线**只报数不判优劣（句长、块数这类形态本身没有好坏），**评估**抓明确的错（漏答、用"不能推出"代替状态、指代要读者自己配对）。

```
git clone <this repo>
cd info-org-eval
pip install -r requirements.txt
python -m infoeval.cli cases/case01 --html out/report.html
```

输出：控制台对照表 + `out/result.json` + 单文件 HTML 报告。

## 一、八项是什么

| # | 对象 | 读者心里问的 | 归属 | 能不能自动 |
|---|---|---|---|---|
| **B1** | 有没有（覆盖） | 我问的几件事都答了吗 | 评估 | 半自动（落点要人配） |
| **B2** | 在哪（定位） | 我要的东西在第几段 | **基线** | ✅ 全自动 |
| **B3** | 散不散（集中） | 同一件事要不要翻几处 | **基线** | ✅ 全自动 |
| **B4** | 层级（结构形态） | 块怎么切、层级多深 | **基线** | ✅ 全自动 |
| **B5** | 状态 vs 推理 | 那到底什么状态 | 评估 | 定位自动，分档要人 |
| **B6** | 有没有废话 | 删了我会少知道什么 | **观察（不计分）** | 定位自动，判定有争议 |
| **B7** | 指代清不清 | "这一项"是哪一项 | 评估 | 扫描自动，判定要人 |
| **B8** | 数量自述对不对 | 到底几件事要我拍板 | 评估（零争议） | ✅ 全自动 |

**为什么分两半**：判断一个对象归哪边，看的不是"能不能自动算"，而是**这个数本身有没有好坏**。

- 句长 28 字 vs 24 字，谁更好？**没有定论** → 基线
- 说"三组"实际四组 → **明确是错** → 评估

## 二、case 目录怎么放

```
cases/你的case名/
├── case.md          # 题目（用户问的那句话）
├── a.md             # 回答 A
├── b.md             # 回答 B
└── aspects.json     # 诉求清单 + 落点（B1/B2 的输入）
```

`aspects.json` 是唯一需要人工写的东西：

```json
{
  "meta": {"case_id": "L0-BRF-006-C001", "task_type": "决策分析",
           "a_name": "回答 A", "b_name": "回答 B",
           "human_preference": "B"},
  "qud": [
    {"id": "Q1", "question": "两个方案各自怎样、有什么影响？"},
    {"id": "Q2", "question": "应该选哪个方案？"},
    {"id": "Q3", "question": "现在需要拍板什么？"}
  ],
  "aspects_a": [
    {"id": "aspect_1", "label": "比较两个方案", "blocks": [1],
     "keywords": ["方案A", "方案B"], "verdict": "有"}
  ],
  "aspects_b": [ ... ]
}
```

- `blocks`：这个诉求落在第几个语块（**0 = 第一个标题之前的开头段**）
- `verdict`：`有` / `部分` / `无` —— **由人或 LLM 判定后手填**
- `keywords`：只用于交叉校验（看配置说"有"但关键词一次都没出现这种矛盾），**不参与判定**
- `qud`：B5 的预设问题，从 `case.md` 里抽

**脚本不会替你判 `verdict`**。这是设计选择：覆盖判定的语义成分重，机器的判断不可复核。

## 三、结果怎么读

### 基线三项（只报数，没有阈值）

| 指标 | 说什么 |
|---|---|
| **B2 位置%** | 某个诉求第一次出现在全文百分之几处。**越小越早** |
| **B3 延续率** | 相邻两句是否共用同一个实体。**越高越连贯** |
| **B3 集中度** | 高频主题词撒得多开。**1 = 只在一块，0 = 每块都有** |
| **B4 列表项平均字数** | 45 字/条 = 段落伪装成列表；19 字/条 = 一条一件事 |

**阈值等样本积累到几十组后再划。现在这些数只能告诉你"两份回答长得不一样"，不能告诉你"哪份好"。**

### 评估项

| 指标 | 怎么判 |
|---|---|
| **B1 缺口** | `aspects.json` 里 verdict 为"无"的诉求 |
| **B5 ②档数** | 半状态+推理：关键状态缺失，用"不能推出"代替 |
| **B7 需配对数** | 同一句出现两个指代（"前一份/后一份"），读者要回前文数对象 |
| **B8 不一致数** | 声明数与实际列举数不符 |

### 必须看分布，不能只看均值

B3 的 `共享强度分布` 一定要看。实测过一次：词面重叠（连续值）说 A 更连贯，实体延续率（二元值）说 B 更连贯——**因为一批"两极分化"和"均匀型"的文本，均值是同一个数。**

## 四、三条最要紧的口径

### ① 语块（`blocks` 和位置%的单位）

按标题切。但**不能只认 Markdown `#`**：

- 有的回答全文没有 `#`，标题是「独立短行」（`建议结论`、`推荐执行顺序`）
- 有的回答全文**没有一个空行**，靠空行分段会算成 1 段
- 有的回答里的表格被压平成文本，**每个单元格都是短行**——当成标题会凭空多出 7 个块

三种都处理了（见 `infoeval/units.py` 的 `table_zone()` 和 `is_heading()`）。

### ② 作者句（所有句级指标的单位）

按 `。！？` 切，**不切分号**，然后排除：

- 独立短行标题
- 压平表格的单元格
- 来源标签（`已确认安排`、`发包通知`）

但**保留引导句**（以「：」结尾且含动词的，如「建议直接拍板：」）——它们是作者句，也正是 B6 要判的对象。

**这一步不做，回答 B 那种结构化回答会有 37% 的"句子"其实是标题和表格格。**

### ③ 位置% 的分母用清洗后正文

去掉 markdown 装饰符和链接 URL 再算。

实测过：一份回答 26.8% 的字符是 `[原消息](<https://example.com/...>)` 这种长链接和加粗标记，直接算会把位置% 偏 4.5 个点。

## 五、已知边界

| 项 | 状态 |
|---|---|
| **B6 不计分** | 四种口径给出三个方向。引导句在删句测试下必然判无效，但它帮助扫读——这是构造性矛盾，不是判定误差 |
| **B5 三档判定是我设计的** | 框架来自 QUDeval，但三档划分无直接文献出处；需第二评者验证 |
| **B1 的 aspects 要人抽** | 抽漏了就会误判"没缺口" |
| **位置% 依赖语块识别** | 已修表格误判，但新格式仍可能错。字符类指标（跨度）不受影响 |
| **实体抽取是位置启发式** | 句首第一个名词当主语、动词后第一个当宾语，非依存句法分析 |
| **共指不解** | 纯词面。「前一份 → PPT」这类看不见 |
| **单份样本** | 一套 case 只说明这一题，不能推广 |

## 七、代码结构

```
infoeval/
├── units.py              切分层：语块 / 作者句 / 表格区识别   ← 地基
├── entities.py           实体抽取（供 B3）
├── syntax.py             句长 / T-unit（A、B 共用）
├── b_coverage_position.py   B1 + B2
├── b3_dispersion.py       B3
├── b4_structure.py        B4
├── b5_state.py            B5（定位器）
├── b6_verbosity.py        B6（定位器）
├── b7_anaphora.py         B7
├── b8_declaration.py      B8
├── core.py                主流程 + 对照表
├── report.py              单文件 HTML
└── cli.py                 命令行
```

**`units.py` 是最重要的文件**——所有指标都建立在它上面，切错则全错。改任何东西之前先读它。
